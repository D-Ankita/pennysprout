# PennySprout Exact Database Schema

The executable schema is the ordered set of migrations in [`supabase/migrations/`](../supabase/migrations/): [`0001_initial_schema.sql`](../supabase/migrations/0001_initial_schema.sql) and [`0002_app_sessions_and_error_reports.sql`](../supabase/migrations/0002_app_sessions_and_error_reports.sql). pgTAP tests live in [`supabase/tests/database/`](../supabase/tests/database/). This document explains the contract implementers must preserve.

## 1. Ownership and identity

- `profiles` extends `auth.users` with non-sensitive display data.
- `private.login_identities` maps normalized usernames to random, unguessable internal Auth aliases; `private.login_controls` supports lockout. Neither is exposed to authenticated clients.
- `households` owns all product data and defines currency/timezone.
- `household_members` grants one role per user per household and tracks invitation status.
- Beta assumes one active membership per user in the app, while every data key remains household-scoped.

`private.app_sessions` stores one row per Supabase Auth session (`session_id` from the JWT) with `last_activity_at` and an optional revocation (`SIGNED_OUT`, `INACTIVITY`, `PASSWORD_CHANGED`, `ADMIN_RESET`, `MEMBERSHIP_DISABLED`). `public.has_active_app_session()` is true only for an unrevoked row owned by `auth.uid()` and used within 30 days. `is_active_household_member`, `has_household_role` and the `profiles` RLS policy all require it, so every household read and RPC enforces the 30-day inactivity rule without Supabase's paid session settings.

All references to a Child use the composite membership key `(household_id, child_user_id)`, not an unconstrained user UUID.

## 2. Tasks and recurrence

- `tasks` stores the current Admin-approved definition and a monotonically increasing `version`.
- `task_schedule_weekdays` stores selected weekdays relationally; recurrence rules are not hidden in arbitrary JSON.
- `task_proposals` stores typed, validated proposed fields plus `base_task_version` for stale-write detection.
- `task_completions` snapshots task title, task version, default reward, local occurrence date, and occurrence key.
- `completion_verifications` is separate so verification cannot accidentally become an approval gate.

`occurrence_key` format is generated by trusted recurrence logic and treated as opaque by clients. Expected forms are `once`, `day:YYYY-MM-DD`, and `week:YYYY-MM-DD`, where dates are calculated in the household timezone.

The unique slot `(task_id, child_user_id, occurrence_key, occurrence_sequence)` identifies every submission attempt. The submission function allocates the next sequence under a task/child advisory lock, separately enforcing the configured pending/approved completion limit and maximum three rejected attempts.

## 3. Finance

- `ledger_transactions` is an immutable business-event header.
- `ledger_postings` contains signed effects on `SPENDABLE`, `SAVINGS`, or `UNPAID_EARNINGS`.
- `wallet_balances` is a projection view, never stored mutable state.
- `expense_correction_requests` and `savings_withdrawal_requests` model Admin-reviewed workflows.
- `savings_goals` and optional `savings_goal_allocations` add reporting without changing account truth.
- `goal_archive_requests` enforces Admin-reviewed goal archival.

Uniqueness constraints on transaction references provide the final idempotency barrier for completion rewards, approved withdrawal requests, and reversals.

## 4. Audit and idempotency

- `audit_events` records actor, event, entity, and before/after-safe metadata.
- `idempotency_keys` records command name, request hash, status, and response identifiers.
- `notification_outbox` makes push delivery retryable without making notifications part of a core transaction's success condition; `push_tokens` remains user-owned device registration data.
- Request payloads must be canonicalized before hashing. The same key may only be reused with the same authenticated user, command, and hash.

Audit metadata must not contain auth tokens, secrets, or unnecessary child personal data.

- `private.client_error_reports` is the free crash-report store. It is append-only (updates rejected by trigger), has no client grants and is written only through `report_client_error`. Columns are limited to user, server-derived household, random device-install ID, error code, app version/build, environment (`local`/`family`), platform (`android`), route template, occurrence/receipt times and an optional sanitized stack of at most 4,000 characters. Rows older than 30 days are removed in bounded batches by later reports.

## 5. Mutation boundary

Authenticated clients have read-only table access where RLS permits it. Every product mutation, including creation of pending requests, goes through a named function with explicit role and invariant checks:

PostgreSQL grants function execution to `PUBLIC` by default. Each function migration must revoke that default before granting only `authenticated` or `service_role` according to `API_CONTRACTS.md`. `SECURITY DEFINER` functions use an empty search path and fully-qualified object names.

- `approve_completion`
- `reject_completion`
- `decide_task_proposal`
- `record_expense`
- `decide_expense_correction`
- `deposit_to_savings`
- `decide_savings_withdrawal`
- `submit_goal_archive`
- `decide_goal_archive`
- `record_payout`
- `reverse_payout`
- `create_adjustment`

The initial migration establishes tables, constraints, indexes, immutable-ledger triggers, helper functions, grants, and base RLS. Individual command functions may be delivered in follow-up migrations phase-by-phase, but their signatures and invariants must follow the state-machine and financial-model documents before any client screen depends on them.

## 6. Deletion policy

- Memberships are disabled, not deleted.
- Tasks and goals are deactivated/archived, not deleted after use.
- Completions, verifications, reviews, ledger records, and audit events are never client-deleted.
- A hard-delete retention policy, if ever required for legal/privacy reasons, is a separate privileged operational process and must preserve required financial/audit obligations.

## 7. Migration rollout

For the first empty beta database:

1. Apply the migration locally.
2. Run schema and RLS integration tests using separate Child, Parent, Admin, and unrelated-household identities.
3. Seed the beta household through the local-only seed script using real Auth user IDs.
4. Apply to the hosted Supabase Free family project only after local tests and an encrypted logical backup.
5. Connect through the shared session-mode pooler (never the paid IPv4 add-on), take the encrypted logical export first and record the applied migration version.

This migration has not been applied to any remote Supabase project merely by being committed to the repository.
